## 三、课后作业 1：`llm.py` 增强说明

本次选择的增强方向是**调用耗时与 Token 用量统计，为费用估算提供依据**。

我在 `llm.py` 的 `ask` 方法中引入 `time` 模块，记录每次调用的耗时并输出结果；同时，在 `APIEngine` 中捕获并打印 Token 用量。Token 用量可以作为后续估算云端调用费用的依据；若要输出具体费用，还需要根据所用模型的输入、输出 Token 单价进行计算。

作为未来的教师，了解本地模型的响应速度与云端 API 的延迟、用量和潜在成本，有助于合理安排教学任务。例如，课堂中的即时互动可以优先使用本地模型；需要较复杂推理或更高质量文本的任务，可以在数据合规且成本可接受的前提下调用云端模型。

## 四、课后作业 2：什么任务固定走本地或云端？（约 200 字反思）

通过本次五组边界测试，我认识到，引擎选择应综合考虑数据隐私、任务难度、响应速度和输出质量。涉及学生姓名、成绩等敏感信息的任务，应优先使用本地模型，并避免在本地故障时自动将原始数据发送到云端；确需调用云端时，应先进行适当脱敏。对于复杂教案设计、多步推理和长篇材料分析，可以在确认数据允许外传后使用云端模型，并对结果进行核验。默认策略可设为普通、非敏感任务优先走本地，故障时再回退云端；敏感任务则应采用禁止云端回退的策略。本次测试也表明，程序能够自动切换引擎并不等于答案可靠，教师仍需对生成内容进行事实核查与专业审核。

## 五、课后作业 3：RAG 预习思考

RAG（检索增强生成）的核心思路可以通俗地理解为“让 AI 开卷回答”：模型生成答案前，先从指定资料中检索相关内容，再将检索结果作为上下文提供给模型，以减少仅凭参数记忆回答所产生的错误。

例如，我计划准备《国际中文教育中文水平等级标准》（GF0025—2021）中有关四级词汇指标的节选文本，并保存为 TXT 文件。根据该标准的语言量化指标总表，四级词汇为**本级新增 1000 个、截至四级累计 3245 个**；这两个数字含义不同，不能将“本级新增量”误写成“累计总量”。后续可以通过代码检索这段资料，并要求模型依据检索到的文本回答问题。

我也认识到，RAG 并不能彻底杜绝幻觉。检索内容是否相关、资料版本是否正确、上下文是否完整，以及模型是否忠实依据资料作答，都会影响结果。因此，构建 RAG 系统时还需要检查检索结果，并尽可能让答案标明依据，便于核验。
